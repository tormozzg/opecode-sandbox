= Opencode Java Sandbox

== Build docker image

`./build-image.sh [image_name] [jdk_packages] [java_default]`

Without the second argument the script builds the JDK-free base image from
`Dockerfile` and tags it with the given name. Example:

`./build-image.sh oc-sandbox`

With the second argument the script builds in two steps: first it builds the
base image from `Dockerfile` and tags it as `oc-sandbox-base`, then it builds
the requested image from `Dockerfile.jdk`, which inherits the base via `FROM`
and installs every JDK package (space-separated sdkman identifiers) with
sdkman. Example:

`./build-image.sh oc-sandbox-jdk "8.0.452-zulu 17.0.12-zulu 25.0.4+1.1-zulu"`

The *last* package in the list is special: it is the JDK that the LSP
servers and linters always run with (jdtls 1.63+ requires Java 25), and the
default `sdk default java` version.

The optional third argument overrides the default java version (any of the
installed packages). Example with Java 17 as the default:

`./build-image.sh oc-sandbox-jdk "8.0.452-zulu 17.0.12-zulu 25.0.4+1.1-zulu" 17.0.12-zulu`

The base image tag `oc-sandbox-base` is built by the script itself and is
expected to exist locally for the second build.


== Host user mapping (UID/GID)

The image contains an unprivileged `opencode` user, created from the
`USER_ID` / `GROUP_ID` build args.

* On Linux the script passes your own `id -u` / `id -g`, so bind-mounted
  files (the project directory and `~/opencode/sandbox/*`) stay owned by you
  inside the container.
* On other platforms (macOS) the `Dockerfile` defaults `1000:1000` are used:
  Docker Desktop virtualizes file ownership, so the host IDs do not have to be
  mirrored inside the container. The macOS default GID 20 (`staff`) also
  already exists in Debian as `dialout`, so passing it breaks `groupadd`.


== Prepare directories

Prepare the host directories the sandbox mounts:

[source, bash]
----
mkdir -p ~/opencode/sandbox/{data,state,config,cache,gradle}
----


== Run the sandbox

The sandbox always runs through the `oc-sand-stateful` script, which keeps
the container around between sessions: anything the agent wrote inside the
container *outside* the mounted directories (e.g. packages installed into
the image filesystem, files in `/tmp`, tool caches) survives across
sessions.

[source, bash]
----
./oc-sand-stateful <image-name>
----

Pass the image you built with `build-image.sh` as the first argument; the
script has no hardcoded default image.

Container naming:

* The container is named `oc-sand-<project>`, where `<project>` is the
  basename of the directory you run the script from. One container per
  project.

Behavior:

* No container exists yet -> `docker run` (without `--rm`) creates and starts
  it.
* Container exists but is stopped -> `docker start -ai` resumes it.
* Container is already running -> a message is printed and
  `docker exec -it <container> opencode` attaches a new opencode session.
* All arguments after the image name are forwarded verbatim to `opencode`
  inside the container (e.g. `auth login`, `--version`, `serve`) — except
  the reserved word `wipe-data`, described below; the same
  container-state rules apply, but the command runs with
  `docker exec -it <container> opencode <args...>` instead of starting the
  TUI. A missing container is created detached (running `sleep infinity`),
  a stopped one is started first.
* Shared docker network: before creating or starting the container, the
  script ensures the docker network `mcp-shared-network` exists (created
  with the default bridge driver if missing) so the sandbox container can
  reach MCP servers attached to the same network. New containers join it
  at creation time via `--network`; a pre-existing container that is not
  on the network yet is connected with `docker network connect` on the
  next run. The `wipe-data` mode neither creates nor requires the network.

Optional arguments:

* `wipe-data` (as the first argument after the image name; a reserved word):
  removes the project container with `docker rm -f` so the next run creates
  a fresh one. Use this after rebuilding the image so the new container
  picks up the updated image. The script does not create or start
  anything, and exits 0 whether or not the container existed:
+
[source, bash]
----
./oc-sand-stateful <image-name> wipe-data
----

Passing arguments to opencode:

* With extra arguments after the image, the script makes sure the container
  exists and is running (creating it detached or starting it if stopped),
  then runs `opencode <args...>` inside it with `docker exec -it`:
+
[source, bash]
----
./oc-sand-stateful <image-name> auth login
./oc-sand-stateful <image-name> auth list
./oc-sand-stateful <image-name> --version
./oc-sand-stateful <image-name> serve
----


== Docker access inside the sandbox

The host docker socket is passed into the container so the docker CLI (and
Testcontainers) inside the sandbox act on the host daemon — sibling
containers, not a nested daemon:

* on Linux `/var/run/docker.sock` is mounted and the container joins the
  socket's GID (the `docker` group);
* on macOS `~/.docker/run/docker.sock` (fallback `/var/run/docker.sock`) is
  mounted and the container gets GID 0, because Docker Desktop exposes the
  socket as `root:root` `0660` inside the container. The old hardcoded
  `--group-add 959` only matches a Linux host.

`TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal` is exported for
Testcontainers, which then reaches the containers it starts on the host.

The docker CLI itself is not part of the image: install it once inside the
container (`sudo apt-get install -y docker-cli`), the stateful container
keeps it.


== Java / Kotlin tooling

`Dockerfile.jdk` installs all requested JDKs side by side via sdkman, plus:

* `jdtls` — Eclipse JDT Language Server (Java LSP), in
  `~/.local/share/jdtls`; the `~/.local/bin/jdtls` wrapper pins it to the
  *last* JDK of `JDK_PACKAGES` (Java 25), because jdtls 1.63+ requires a
  Java 25 runtime; the server itself compiles projects from Java 1.8
  through 25, so even Java 8 projects get full LSP support;
* `kotlin-lsp` — JetBrains Kotlin Language Server
  (https://github.com/Kotlin/kotlin-lsp), standalone build with its own
  bundled runtime (independent of the sdkman JDKs);
* `ktlint` — Kotlin linter/formatter, wrapped to run on the last JDK;
* `checkstyle` — Java linter, wrapped to run on the last JDK.

=== Switching the default Java version

At runtime the default version can be overridden per container with the
`JAVA_DEFAULT` environment variable (applied by `entrypoint.sh` on start):

[source, bash]
----
OC_SAND_EXTRA_FLAGS="-e JAVA_DEFAULT=17.0.12-zulu" ./oc-sand-stateful <image-name>
----

Inside a session the version can be switched without restarting:

[source, bash]
----
sdk use java 17.0.12-zulu     # current shell only
sdk default java 17.0.12-zulu # persist until the next JAVA_DEFAULT override
----

=== Connecting to opencode

The sandbox mounts the host directory `~/opencode/sandbox/config` as the
opencode config directory, so register the two LSP servers in
`~/opencode/sandbox/config/opencode.jsonc` (replace the plain
`"lsp": true` entry with the object form, which keeps the built-in servers
enabled and adds the custom ones):

[source, jsonc]
----
{
  "lsp": {
    "jdtls": {
      "command": ["jdtls"],
      "extensions": [".java"]
    },
    "kotlin-lsp": {
      "command": ["kotlin-lsp", "--stdio"],
      "extensions": [".kt", ".kts"]
    }
  }
}
----

Optionally register ktlint as the automatic formatter for Kotlin files
(it rewrites files, add only if you want that behavior):

[source, jsonc]
----
{
  "formatter": {
    "ktlint": {
      "command": ["ktlint", "--format", "$FILE"],
      "extensions": [".kt", ".kts"]
    }
  }
}
----

Checkstyle and ktlint have no MCP server and do not need one: opencode
invokes them directly via `bash` when asked to lint, e.g.

[source, bash]
----
ktlint src/                       # lint Kotlin sources
checkstyle -c /google_checks.xml MyClass.java   # lint Java (bundled config)
----

=== Making the agent lint automatically

Three mechanisms, from hard enforcement to on demand (all live in
`~/opencode/sandbox/config/opencode.jsonc` and the files next to it, so they
survive container recreation):

*1. Auto-formatting (enforced by opencode after every edit)* — the
`formatter` block above: opencode runs `ktlint --format` on `.kt`/`.kts`
after each modification, so unformatted Kotlin never survives an edit.
Checkstyle is deliberately not registered there: it only reports, it cannot
fix files, so it would fail as a formatter.

*2. Lint discipline in the system prompt* — the `instructions` option points
at a rules file next to the config:

[source, jsonc]
----
{
  "instructions": ["java-lint-rules.md"]
}
----

`java-lint-rules.md` tells the agent to run ktlint on every touched
`.kt`/`.kts`, checkstyle on every touched `.java`, re-run the linters over
all changed files before finishing a task, and report the final clean/broken
state — and to never silence a rule without explaining why.

*3. On-demand command* — a `/lint` command in the config:

[source, jsonc]
----
{
  "command": {
    "lint": {
      "template": "Lint the Java and Kotlin sources of this project and fix every finding.\n- Kotlin: run `ktlint` (add `-F`/`--format` for auto-fixable issues, e.g. `ktlint --format 'src/**/*.kt'`).\n- Java: run `checkstyle -c /google_checks.xml <files>` (list files with `git ls-files '*.java'` or `find`).\nReport each finding (file:line, rule), apply fixes, and re-run the linters until they are clean.\nOnly touch code related to the findings.",
      "description": "Run ktlint + checkstyle and fix all findings"
    }
  }
}
----

Run it in the TUI as `/lint`.


== Install as a command

Copy the script somewhere on your `PATH`, e.g. `~/.local/bin`:

[source, bash]
----
mkdir -p ~/.local/bin
cp oc-sand-stateful ~/.local/bin/
----

Then run it from any project directory as `oc-sand-stateful <image-name>`;
the container name is derived from the directory you invoke it from.


== Extra docker flags: OC_SAND_EXTRA_FLAGS

The optional environment variable `OC_SAND_EXTRA_FLAGS` injects additional
docker flags into the `docker run` invocation that creates a *new* container.
It is split on whitespace into separate arguments (no `eval`), so a simple
space-separated string works:

[source, bash]
----
OC_SAND_EXTRA_FLAGS="-e FOO=bar -v /host:/container" oc-sand-stateful <image-name>
----

Notes:

* The flags only take effect when the container is first created. Existing
  containers are started with `docker start -ai` or attached with
  `docker exec -it`, neither of which can change a container's configuration;
  the variable is ignored in those cases. Use `wipe-data` to remove the
  container so the next run creates it with the new flags.
* Typical uses are extra environment variables (`-e NAME=value`) and extra
  mounts (`-v /host/path:/container/path`).


== Project-specific wrapper scripts

If you want image-specific or project-specific defaults, write your own tiny
wrapper script instead of modifying `oc-sand-stateful`. The wrapper sets
`OC_SAND_EXTRA_FLAGS` and execs the main script with a fixed image:

[source, bash]
----
#!/bin/bash
set -euo pipefail

IMAGE="oc-sandbox-jdk25:latest"
export OC_SAND_EXTRA_FLAGS="-e MY_PROJECT_ENV=1 -v $PWD/.secrets:/run/secrets:ro"

exec oc-sand-stateful "$IMAGE" "$@"
----

Save it (e.g. as `~/bin/oc-sand-jdk25`), make it executable with
`chmod +x`, and call it exactly like `oc-sand-stateful` — including the
`wipe-data` mode and opencode arguments, which are forwarded to the main
script. The wrapper assumes `oc-sand-stateful` is on your `PATH` (e.g.
installed in `~/.local/bin`).
